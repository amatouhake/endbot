# Endbot のコマンド

コントローラー権限を持つプレイヤーがゲーム内で入力したり押したりできるもの、つまり `/bot`、`/botgroup`、
`/botscript`、`/botweb` の説明です。権限はサーバーのオペレーターが与えます
([コントローラーの登録](../OPERATIONS.md#3-controller-enrollment))。ロールと、それぞれができることは
[PERMISSIONS.md](../PERMISSIONS.md) にあります。

<a id="quick-start"></a>
## クイックスタート

どのコマンドも対象の Bot を名前で指定します。「選択中の対象」という状態はありません。

```text
/bot Alice spawn
/bot Alice tp me
/bot Alice jump
/bot Alice attack continuous
/bot Alice stop
/bot Alice despawn
```

プレイヤーが `/bot` と入力すると、`/bot menu` と同じく Bot の一覧が開きます。`/bot <name>` は
`/bot <name> menu` と同じくその Bot のメニューを開き、`/bot #group` はグループの操作で同じことをします。
サーバーコンソールでは、`/bot` は今までどおりヘルプの 1 ページ目を表示し、対象だけを指定したときは
メニューがプレイヤー専用だという返事になります。
`/bot help` は常にヘルプの 1 ページ目を表示します。`/bot help <page>` (1-3) は、バニラの Bedrock の `/help` に
ならった、ページ分けのコマンド一覧を表示します。`/bot help <operation>` (例: `/bot help move`) は、その操作で
使えるすべての書き方を短い説明つきで表示します。`/bot list` は、わかっているすべてのプロファイルと、その
接続状態をまとめて表示します。`/bot Alice status` は runtime の状態を表示し、BDS 上にプレイヤーのエンティティが
あるときは、BDS が確定したディメンション、位置、向きも合わせて表示します。その `yaw=` は、`look` の結果や
スクリプトの `status` の `data.look` と同じ [0, 360) の範囲で表します。`look <yaw> <pitch>` を手で入力したときの
返事は、指定した角度をそのまま返します。向きを変える (look) のフォームのスライダーは、入力用に -180..180 の
範囲のままです。フォームから送った値は、360 で割った余りとして適用されます。

```text
--- Endbot ヘルプ 1/3: 接続と状態、テレポート ---
/bot ping | /bot list | /bot help - 疎通確認、Bot 一覧、このヘルプ
/bot menu - Bot 操作フォームを開く (プレイヤーのみ)
/bot <name> spawn - Bot を作成または接続する
/bot <name> resume - 場所を変えずに Bot を再接続する
...
次のページ: /bot help 2 - 詳細: /bot help <command>
```

```text
Endbot ヘルプ: move
/bot <name> move forward|backward|left|right|stop
/bot <name> move forward|backward|left|right for <ticks>
移動は押しっぱなしの入力として続き、stop で止まります。for を付けるとその tick 数で止まります。
```

1 ページ目は接続と状態、テレポート、2 ページ目は移動とアクション、3 ページ目はインベントリ、ワールドへの操作、
高度な接続の管理です。各ページは 1 行を 1 つのチャットメッセージとして送ります。そのため、パイプで区切った
詰め込みの 1 行にならず、Bedrock のチャットで読みやすくなっています。

<a id="command-results"></a>
## コマンドの結果

各操作の返事は、接続状態だけでなく、対象の Bot と、適用した入力や変更を伝えます。例:

```text
/bot Alice move forward       -> Endbot: Alice: 移動を forward にしました
/bot Alice jump               -> Endbot: Alice: jump once を要求しました
/bot Alice use continuous     -> Endbot: Alice: use continuous を始めました
/bot Alice stop               -> Endbot: Alice: 移動とアクションを止めました (sprint と sneak も off)
/bot Alice hotbar 2           -> Endbot: Alice: ホットバーのスロット 2 を選びました
/bot Alice move sideways      -> Endbot: Alice: 不明または正しくない Bot の操作です: move
```

Bot についての返事は、エラーや書き方の誤りも含めて、すべて `Endbot: <Bot>: ` で始まります。look の返事には
yaw と pitch が、ブロック操作の返事にはブロックと面が入ります。名前の変更や接続に関わる返事は、要求された変更を
示します。操作のエラーは操作名を示します。例: `Endbot: Alice: move に失敗しました: Bot is offline`。
これらの返事は、入力が適用されたこと、または要求を受け付けたことを確認するものです。当たり判定、アイテムの消費、
届く距離など、ワールドでの結果は BDS が決めます。結果は `status` と実際のワールドの様子で確かめてください。
接続の処理は非同期のままです (`connecting` は spawn の完了ではありません)。

<a id="control-forms"></a>
## 操作フォーム

プレイヤーは、よく使う操作を入力する代わりに、Bedrock 標準のフォームから実行できます:

```text
/bot               -> Bot とグループの対象一覧 (プレイヤー)、ヘルプ 1 ページ目 (コンソール)
/bot menu          -> 同じ対象一覧
/bot Alice         -> Alice のメニュー (/bot Alice menu と同じ)
/bot Alice menu    -> Alice のアクションと、状態と位置の短い要約
/bot #miners       -> グループの操作メニュー (/bot #miners menu と同じ)
/bot #miners menu  -> 同じ操作メニューを #miners に適用
```

対象一覧には、オンラインの Bot が名前で並びます。接続中、再試行中、失敗した Bot には、暗い色の `接続`、`再試行`、
`失敗` が前に付きます。オフラインの Bot は、1 つの `オフライン (n)...` ボタンの奥にまとめられます。オンラインの
Bot の画面には、すべて止める (stop)、移動 (move、jump、スプリント / スニーク)、向きを変える (look)、テレポート、
ゲームプレイ (攻撃、アイテムを使う、ブロックを壊す、ブロックを操作、近くのエンティティ、エンティティを操作、降りる)、
インベントリ (持ち物を表示、hotbar、hold、swap、drop)、Bot (resume / spawn、reconnect、確認つきの despawn、
radius、状態) があります。
分類の名前は Minecraft の操作設定にならっています。オフラインの Bot では、resume / spawn、radius、Bot の設定の
分類が使えます。Bot ごとのプロファイルの操作として、名前の変更と確認つきの forget があります。forget は
オフラインのプロファイルにしか使えません。
対象一覧には `#group (count)` の項目もあり、この同じ操作画面を直接開きます。グループ全体の操作は、オフラインの
メンバーが混じっていても使え、失敗は操作ごとに報告されます。名前の変更と forget は 1 体の Bot が対象です。
一覧の並びは、`/bot` 自体が指定できるものの順です。オンラインの Bot、`オフライン (n)...` の一覧、
`#group (count)` の対象、そして `+ ここに新しい Bot` です。作成の後にリンクが 2 つ続きます。**グループを管理...** は
`/botgroup menu` を開き、スクリプトが有効なら **スクリプト...** が `/botscript menu` を開きます。グループの管理は
`/bot` の操作ではないので、対象の中には並ばず、このリンクとしてだけ表示されます。
入力フォームでは、ドロップダウン、スライダー、テキスト欄を使います。フォームを閉じる (または despawn の確認を
キャンセルする) と、開く前の画面に戻ります。座標の欄はコマンドと同じ `~` の書き方を受け付け、欄のラベルに `~` が
何からの相対かが書いてあります。送信するとフォームが閉じ、いつものチャットの返事が表示されます。続けるには、
もう一度 `/bot` を実行してください。

ジャンプ (jump)、攻撃 (attack)、アイテムを使う (use)、ブロックを壊す (destroy) は、コマンドの書き方をそのまま
映していて、フォームだけの意味は加えません。最初の画面には、コマンドのモード (`once`、`continuous`、`interval`、
`stop`、それに use では `for`、destroy では `x y z`) が並びます。パラメーターのないモードは、すぐに実行されます。
パラメーターのあるモードは、その句だけのフォームを開きます。句の名前はコマンドと同じで、単位は tick です
(`interval <ticks>`、`hold <ticks>`、`for <ticks>`。ブロックを壊す (destroy) の continuous のフォームには
`count <blocks>` もあります。20 で 1 秒)。任意の句を空欄にすると省略されます。そのため `for` が空欄なら止めるまで
続き、`count` が空欄ならブロック数の制限はありません。アイテムを使う (use) の `once` は `hold` を受け付けるので、
フォームを開きます。
たとえば、ためた弓を 3 回撃つには、`interval...` で interval 30、hold 20、for 80 にします。歩く (move) は
`move <direction> [for <ticks>]` のフォームを 1 つ開きます。短く 1 回だけ動くのは、コマンドの入力に任せています。
フォームやボタンが実行するコマンドは、いつもの返事の前に、入力したときの形でチャットに灰色で一度表示されます。
例: `/bot Alice use interval 30 hold 20 for 80`。メニューの移動は表示されません。

フォームは、コマンドを入力するもう 1 つの方法にすぎません。ボタンやフォームの送信は、どれも同じ意味の `/bot` の
引数 (例: `/bot Alice attack interval 40`) になり、同じ権限チェック、コマンドの待ち行列、パーサー、返事を通ります。
そのため、入力したコマンドとフォームの送信は必ず同じように動きます。フォームを開いている間に権限を取り消された
コントローラーが送信すると、いつもの権限の返事が出ます。サーバーコンソールはフォームを開けません
(`/bot menu` は `/bot help` を案内する返事をします)。高度な `tp ... facing ...` の引数と、ヘルプの詳細ページは
コマンドだけです。座標を指定した spawn、ブロックの操作、Bot ごとのプロファイルの名前の変更と forget には、
フォームの操作があります。

画面の内容、すべてのフォームの応答がパーサーの受け付ける引数になること、不正な応答、画面の送信と取り消しは、
ユニットテストで確かめています。実際のクライアントでの表示と入力は、手動の確認です。通常の Microsoft/Xbox
クライアントで `/bot`、`/bot menu`、`/bot <name>`、`/bot <name> menu` を開き、各入力フォームを一度ずつ送信し、
despawn の確認をキャンセルし、Escape でフォームを閉じます。そして、権限を取り消されたコントローラーが、
すでに開いているフォームから操作できないことを確かめます。

<a id="reply-language"></a>
## 返事の言語

返事、ヘルプ、フォームの画面は、英語と日本語で表示できます。既定 (`endbot.toml` の `[ui] language = "auto"`、
[OPERATIONS.md](../OPERATIONS.md) の 2 節を参照) では、各プレイヤーにゲームクライアントの言語が使われます。
日本語のクライアントでは日本語、それ以外のクライアントでは英語です。`language = "en"` または `"ja"` にすると、
すべてのプレイヤーで 1 つの言語に固定されます。

変わるのは言葉づかいだけです。コマンドの単語と書き方は、どの言語でも英語のままです。ヘルプは
`/bot <name> move forward|backward|left|right for <ticks>` を日本語の説明つきで表示します。フォームのモードの
ボタンや句の欄も、コマンドの名前 (`once`、`continuous`、`interval <ticks>`、`for <ticks>`) のままです。そのため
フォームを使ううちに入力するコマンドを覚えられ、フォームのコマンドの灰色の表示も変わりません。サーバーコンソール、
サーバーのログ、コマンドの入力補完に出る `/bot` の説明は英語のままです。Endbot runtime から来るメッセージ
(例: Bot が見つからない) は翻訳されません。続いているジョブからの通知 (連続採掘の終了など) は、そのジョブを始めた
プレイヤーの言語で表示されます。そのログの記録は英語のままです。

日本語の文章には、かな、漢字、ASCII、日本語の読点と句点だけを使います。Bedrock のチャットのフォントには多くの
記号がない (矢印は四角で表示される) ためです。実際のクライアントでの見た目は、手動の確認です。日本語の
クライアントで、`/bot help` の 1-3 ページ、`status` の返事、エラー、Bot の一覧と Bot の画面、モードのフォームを
1 つ読みます。

<a id="mining-blocks"></a>
## ブロックの採掘

```text
/bot Alice hotbar 1
/bot Alice destroy
/bot Alice destroy once
/bot Alice destroy continuous
/bot Alice destroy continuous for 200
/bot Alice destroy count 64
/bot Alice destroy continuous for 200 count 64
/bot Alice destroy 100 64 -20
/bot Alice destroy ~ ~-1 ~ up
/bot Alice destroy stop
/bot Alice destroy acacia_log within 6 except ~ ~-1 ~ count 20
/bot Alice status
```

`destroy` は、`jump`、`attack`、`use` と同じモードの単語を使います。`once` (既定)、`continuous`、`stop` です。
`interval` モードはありません。`continuous` がすでに次のブロックを待つからです。

`destroy` (または `destroy once`) は、Bot の今の視線上で 6 ブロック以内にあるブロック 1 つに、左クリックの長押しを
始めます。座標を明示すると、届く位置にあってさえぎられていないブロック 1 つを対象にし、Bot をそのほうへ向けます。
面は省略でき、`interact` と同じ名前を使います。
草、花、たいまつなど当たり判定のないブロックは、名前で指定したブロックをさえぎりません。一方、照準はプレイヤーと
同じようにそこで止まります。拒否されたときは、間にあるブロックの名前が出ます
([ブロックの狙い方](../SCRIPTING.md#targeting-blocks)を参照)。
相対座標は Bot から測ります。サーバーコンソールからのコマンドでも同じです。開始時に、移動、攻撃、アイテムの使用の
入力はクリアされます。先に `hotbar` で使う道具を選んでください。採掘は歩きも道具の選択もしません。

`destroy continuous` は、Bot の今の視線の方向に左クリックを押し続けます。BDS が対象を更新するたびに、同じ線上の
次の届くブロックを選びます。6 ブロック以内に対象がない (または岩盤のような壊せないブロックが前にある) ときは
待ちます。
届くブロックを視線の先に置くと、採掘は自動で再開します。Bot はその場にとどまり、選んだ範囲を掘り進めることは
しません。この待機と再開、そして進行中の破壊をやめるには、`destroy stop` を使います。
`destroy for <ticks>` (または `destroy continuous for <ticks>`) は、コマンドからその入力 tick 数だけ連続採掘をして
終わり、壊している途中のブロックはやめます。1 ブロックの `destroy` と座標指定には `for` も `count` も付けられず、
10 分の安全のためのタイムアウトのままです。時間が終わると、始めたコントローラーに info レベルのメッセージ
`Endbot: Alice: destroy continuous が止まりました: 指定の時間が終わりました` が 1 回届きます。実行中は、`status` に
残りの tick 数が表示されます。

`destroy count <blocks>` (または `destroy continuous count <blocks>`) は、その数のブロックがなくなるまで連続採掘を
して、終わります。数えるのは BDS が完了した対象なので、壊している途中のブロックは最後まで壊し、次のブロックを待つ
時間は数に入りません。実時間で数える `for` と違い、count はサーバーの負荷、TPS、ブロックの間の待ち時間に
左右されません。`for` と `count` はどちらの順でも組み合わせられ、先に来たほうで採掘が終わります。そのとき、それに
合った info レベルのメッセージ (`... が止まりました: 指定のブロック数に達しました`) が出ます。`status` はモードの後に
ここまでのブロック数を表示します。例: `1 64 2 の minecraft:stone を採掘中 (continuous, 12/64 ブロック)`。終わった
実行は合計を残します。例: `前回の destroy: 指定の時間が終わりました (137 ブロック, 1 64 2 の minecraft:stone)`。

BDS は通常のサバイバルの破壊をします。硬さと道具による速さ、ドロップ、耐久値、キャンセルできる
`BlockBreakEvent` の処理も含みます。プラグインが採掘したブロックを空気に置き換えたり、`/setblock` を実行したり、
オペレーター権限を与えたりすることはありません。固定している基準の組み合わせでは、サーバー側で判定するブロック
破壊を使います。ほかの方式は、はっきり拒否されます。

最初の返事は対象を示します。例:
`Endbot: Alice: 1 64 2 の minecraft:stone を壊しています。結果は status で確認できます`。完了のメッセージは送られません。`status` が、採掘の状態をプレイヤー向けの言葉で表示します:

```text
1 64 2 の minecraft:stone を採掘中                                   (今壊している)
1 64 2 の minecraft:stone を採掘中 (continuous, 12/64 ブロック)      (destroy count)
destroy continuous は視線の先のブロックを待っています (前回: ..., 3 ブロック)  (destroy continuous、届く範囲に何もない)
前回の destroy: ブロックが壊れたか変わりました (1 64 2 の minecraft:stone)  (完了)
前回の destroy: 指定のブロック数に達しました (64/64 ブロック, 1 64 2 の minecraft:stone)  (count に到達)
前回の destroy: 失敗: 対象に届きません (...)                         (失敗)
前回の destroy: テレポートで中止 (...)                               (中止)
```

終わったジョブは、次のジョブが始まるまで `前回の destroy` として表示されたままです。1 ブロックの採掘は、BDS が
変わった対象ブロックを送ってきたときに終わります。そのため、置き換えやほかのプレイヤーによる変更でも、その作業は
終わります。連続採掘は次を選び直します。runtime は、すぐに壊れることやドロップを予測せず、サーバーからの更新を
待ちます。拒否された対象や保護された対象は、止めるまで、または 12000 入力 tick のタイムアウト (20 TPS で約 10 分)
まで続くことがあります。

採掘は、ほかの操作をしても続きます。`move`、`look`、`attack`、`use`、`drop`、`interact` では止まりません。
連続採掘は、次のブロックを新しい視線の方向で選びます。ホットバーのスロットや手に持つアイテムが変わる (拾った、
道具が壊れた) と、今のブロックを新しいアイテムでやり直します。テレポート、ディメンションの移動、対象が届かない
位置になること、10 分のタイムアウトのどれかで、今のブロックは終わります。1 ブロックの採掘はそこで終わり、
連続採掘は次の対象を選びます。採掘中に攻撃やアイテムの使用をすると、両方の入力を送ります。結果は BDS が決めます。

採掘が終わるのは、`destroy stop` (採掘だけ)、`stop` (採掘とすべての移動、アクション)、`for` の時間の終了、
`count` の上限への到達、死亡、切断、始めたコントローラーの権限の取り消し、プラグインの無効化のときだけです。
プラグインや制御の worker が応答しなくなったときは、runtime のリース切れ (200 入力 tick、約 10 秒) でも終わります。
連続採掘は、そのコントローラーがログアウトした後も続きます。進行中の採掘は保存されず、再接続しても再開しません。

開始と停止はコマンドの返事で確認でき、サーバーコンソールに info レベルで記録されます。採掘がほかの理由
(1 ブロックの失敗、死亡、切断、権限の取り消し、runtime との接続が失われた) で終わると、始めたコントローラーに
チャットのメッセージが 1 回届きます。例: `Endbot: Alice: destroy continuous が止まりました: 死亡で中止`。
コンソールのログには同じメッセージが warning レベルで記録され、コントローラーがオフラインでも記録されます。
壊せたブロックは通知されません。
狙いはブロックのマス単位で決まります。ハーフブロックやフェンスのような部分的な形も、狙う線を完全なブロックと同じ
ように止めます。一方 `blocks` では、それらは見通せるものとして扱われます
([ブロックの狙い方](../SCRIPTING.md#targeting-blocks))。

実際のサーバーでの確認範囲は、[検証状況](../COMPATIBILITY.md#bot-operations)を見てください。`attack` は、これまで
どおりエンティティへの攻撃です。ブロックには `destroy` を使います。名前はゲームの「攻撃/破壊」の操作に
ならっています。

<a id="linking-the-web"></a>
## ウェブとの連携

ウェブが有効なら、コントローラーは自分のアカウントをゲームから連携します。これができるのは、権限があって Xbox で
認証したプレイヤーだけで、自分のアカウントだけです。

```text
/botweb link     Endbot Web 用のコード: 6 文字、有効 5 分、1 回のみ
/botweb status   このプレイヤーのウェブアカウントの有無と、パスキーとセッションの数 (既定)
/botweb unlink   このプレイヤーのウェブアカウント、パスキー、セッションを削除
/botweb help     この一覧
```

新しいコードを出すと、前のコードは使えなくなります。連携を解除しても、コントローラー権限はそのままです。
[ウェブの設計](../WEB.md)を見てください。

ウェブのテレポートにある「自分の位置へ」は `tp me` です。ゲームにオンラインでいる間に使えます。

<a id="lifecycle"></a>
## 接続の管理

```text
/bot <name> spawn
/bot <name> spawn at <x> <y> <z>
/bot <name> spawn at <x> <y> <z> facing <yaw> <pitch>
/bot <name> spawn at <x> <y> <z> in <dimension>
/bot <name> resume
/bot <name> reconnect
/bot <name> despawn
/bot <name> forget
/bot <name> rename <new-name>
/bot <name> visibility shared|private
/bot <name> owner <GamerTag>
```

`spawn` は必要ならプロファイルを作り、接続してきた UUID の Bot を、既定ではコマンドを出した人の場所に置きます。
サーバーコンソールから座標なしで `spawn` すると、置く場所は BDS が決めます。新しい Bot はワールドのスポーン地点に、
既存の Bot は前回いた場所に現れます。`spawn at <x> <y> <z> in <dimension>` で場所を明示できます。既存のオフラインの
プロファイルを spawn すると、UUID はそのままで、指定した場所に置きます。`resume` は既存のプロファイルを移動せずに
再接続し、BDS 標準のプレイヤーの保存データを優先します。
`reconnect` は、ID も場所も変えずに切断して再接続します。`despawn` は意図してオフラインにした状態で、自動の
再接続も取り消します。`forget` はオフラインのプロファイルにだけ使え、Endbot の登録だけを削除します。BDS の
プレイヤーデータは消しません。オンライン中の名前の変更は UUID を保ち、ログイン名を変えるために自動で再接続します。

`visibility shared` と `visibility private` は、Bot の公開範囲を切り替えます。`forget` や `rename` と同じく、
持ち主かコンソールだけが使えます (S12)。持ち主のいない Bot は共有のままで、拒否されたときはコンソールの `owner`
コマンドが案内されます。そのため、持ち主の仕組みより前からある Bot を、プレイヤーが非公開にして自分のものにする
ことはできません。`owner` を実行できるのはコンソールだけです。`owner` は Bot を、指定したオンラインのプレイヤーか
コントローラーに割り当てます。公開範囲はそのまま保ちます (記録がなかった Bot には、設定の既定値を使います)。

`help`、`list`、`menu`、`ping` は予約された Bot 名です (大文字と小文字は問いません)。ルートのコマンド `/bot help`、
`/bot list`、`/bot menu`、`/bot ping` がこれらを使うためです。これらの名前で Bot を作ることも、Bot をこれらの名前に
変えることも、コマンド、フォーム、スクリプトのどれからでも拒否されます。すでにこの名前を持つプロファイルは、
そのまま使えます。`/bot list` とそのメニューはそれに印を付け、`rename` を勧めます。レジストリ (`operations.json`、
`reservedBotNames`) が、すべての画面が読む唯一の一覧です。

`spawn`、`resume`、`reconnect` は `[limits]` に従います ([設定](../OPERATIONS.md#2-configuration)を参照)。人間の
プレイヤー用に確保された枠を Bot が使うことになるときや、`max-bots` を超えるときは、コマンドは今の数を示して
拒否されます。グループやスクリプトでは、該当するメンバーだけが失敗します。`despawn` と `forget` は制限されません。
上限を下げても、すでにいる Bot はオンラインのままです。

要求した spawn がワールドに届かなかったとき、保留中の配置は resume、reconnect、despawn、forget、rename で
破棄されます。そのため、これらの操作が後で、取り残された spawn の配置を使ってしまうことはありません。

spawn は、プロファイルを作成または開始する前に、座標を解決し、行き先のディメンションを確かめます。最初の spawn
では、オンラインの実プレイヤーの名前も拒否します。既存の Bot は、自分の UUID と名前をそのまま使えます。そのため、
配置が不正でも、接続の管理に副作用は残りません。

名前には、ASCII の英字、数字、アンダースコアを 1–16 文字使います。重複は大文字と小文字を区別せずに判定します。
プラグインは、オンラインの実プレイヤーの名前を拒否します。Endstone は、オフラインの GamerTag の履歴を確実かつ
完全に調べる手段を提供していません。そのため、オペレーターは、知っているオフラインの実プレイヤーの名前を避ける
必要があります。

<a id="teleport"></a>
## テレポート

```text
/bot Alice tp me
/bot Alice tp Steve
/bot Alice tp 100 64 -20
/bot Alice tp 100 64 -20 90 0
/bot Alice tp 100 64 -20 facing Steve
/bot Alice tp 100 64 -20 facing 100 70 -10
/bot Alice tp in nether 100 64 -20
```

`overworld`、`nether`、`end` は、Minecraft の名前空間付き ID に対応します。名前空間付き ID をそのまま書くことも
できます。`~` による相対の行き先と `facing` の座標は、どちらもコマンドを出した時点の同じスナップショットから
解決します。テレポートには `Actor.teleport` を使います。バニラの `/tp` は実行せず、チートコマンドの権限も
必要ありません。

同じディメンション内でサーバーがテレポートさせた後、runtime はその位置の補正を受け入れ、通常のクライアント側の
予測による上下の移動に戻ります。そのため、足場のない空中にテレポートされた Bot は、テレポート先の高さを送り
続けるのではなく、落ちて着地します。

ディメンションの移動では、古い移動の予測とエンティティの対象をリセットし、ディメンションの切り替えと読み込みを
受け入れ、設定したチャンク半径を要求するようになりました。ノックバックのため、サーバーからの動きを移動の予測に
取り込みます。
ディメンションの移動、ポータルでの移動、移動直後のノックバックの後に、2 人の人間のクライアントで Bot の位置が
一致するかは、まだ確かめていません ([#274](https://github.com/amatouhake/endbot/issues/274))。

<a id="chunk-loading-range"></a>
## チャンクの読み込み範囲

```text
/bot Idle radius 5
/bot Explorer radius 12
/bot Explorer radius
/bot Explorer radius default
```

`radius` は 2..32 チャンクを受け付けます。Bot ごとの設定がなければ、`endbot.toml` の `[runtime].chunk-radius` が
使われます (既定は 5)。半径の設定は指定した Bot だけに効き、オンラインなら再接続せずに、すぐ新しい要求を送ります。
登録済みのオフラインの Bot も設定できます。この設定は、再接続、名前の変更、runtime の再起動の後も残ります。
`default` で設定を外すと、共通の設定に戻ります。`radius` か `status` で問い合わせると、要求した値、その出どころ、
サーバーの答えが表示されます。例: `Endbot: Alice: チャンク半径 12 (この Bot の設定)、サーバ確認済み 10`。
変更の直後はサーバーがまだ答えていないので、返事は `サーバの確認待ち` になります。もう一度問い合わせると、
確定した範囲が表示されます。オフラインの Bot では `オンライン時に反映` と表示されます。

必要に応じて、止まっている Bot には小さい範囲を、探索する Bot には大きい範囲を要求してください。BDS はどちらの
要求も制限することがあります。今の基準の組み合わせでは、3 の要求が 5 に引き上げられました。この設定はサーバーの
シミュレーション距離を変えません。また、これだけで Bot が動いたり、ある範囲の地形の生成が保証されたりはしません。
[オペレーター向けの設定](../OPERATIONS.md)を見てください。

<a id="inputs-and-actions"></a>
## 入力とアクション

```text
/bot Alice move forward|backward|left|right|stop
/bot Alice look <yaw> <pitch>
/bot Alice look at <x> <y> <z>
/bot Alice move forward|backward|left|right for <ticks>
/bot Alice jump|attack|use [once|continuous|interval <ticks>|stop]
/bot Alice jump|attack|use [continuous|interval <ticks>] for <ticks>
/bot Alice use for <ticks>
/bot Alice use hold <ticks> [interval <ticks>] [for <ticks>]
/bot Alice sprint on|off
/bot Alice sneak on|off
/bot Alice inventory
/bot Alice hotbar
/bot Alice hotbar <1-9>
/bot Alice swap <a> <b>
/bot Alice hold <item>
/bot Alice interact [<x> <y> <z> [face] | <block type> [within <area>] [except <area>] | @<type|id|nearest>]
/bot Alice attack @<type|id|nearest> [once|continuous|interval <ticks>|stop] [for <ticks>] [count <n>]
/bot Alice interact @<type|id|nearest> [once|continuous|interval <ticks>|stop] [for <ticks>] [count <n>]
/bot Alice interact stop
/bot Alice destroy <block type> [continuous] [for <ticks>] [count <blocks>] [within <area>] [except <area>]
/bot Alice destroy continuous [for <ticks>] [count <blocks>] [within <area>] [except <area>]
/bot Alice entities
/bot Alice entity [@<type|id|nearest>]
/bot Alice target
/bot Alice block <x> <y> <z>
/bot Alice blocks <type> [limit <1-64>] [within <area>] [except <area>]
/bot Alice dismount
/bot Alice drop
/bot Alice drop stack
/bot Alice drop <1-36|offhand|head|chest|legs|feet>
/bot Alice drop <item> [count]
/bot Alice drop all
/bot Alice stop
```

アクションのモードを省くと `once` になります。continuous のアクションは、20 Hz の入力 tick ごとに実行されます。
interval のアクションには 1–72000 tick を指定できます。移動は押しっぱなしの入力として動きます。全体の `stop` は、
移動、予定されたアクション、スプリント、スニークをクリアし、セッションは接続したままにします。`look` は stop の
後も最後の向きのままです。
`look` は、BDS が新しい向きを報告した時点で答えます (1 度以内、約 0.5 秒まで: 20 TPS で 10 tick)。そのため、直後に
送った `attack`、`use`、`destroy`、`interact` は、新しい視界に対して動きます。BDS が時間内に報告しないと、`look` は
タイムアウトで失敗しますが、Bot は向きを変えていることがあります。yaw の単位は度で、0 が南 (+Z)、90 が西 (-X)、
180 が北、270 が東です。どんな値も受け付けます (360 で割った余りを使います)。pitch は -90 (上) から 90 (下) です。
`use` は、手に持ったアイテムの通常の Bedrock の操作を送ります。手が空なら何も起きず、安全です。Endbot がアイテムを
作り出したり、サーバーコマンドを実行したりすることはありません。
スプリントとスニークは、Bedrock の 1 tick の開始と終了の切り替えに加えて、押し続けている状態のフラグも送ります。
再接続で入力をリセットしても、前の接続での切り替えを送り直すことはありません。

`inventory` は、サーバーのスレッドで Endstone を通して、確定した持ち物を読みます。空でないスロットだけを、
`minecraft:` を除いた ID と個数で表示します。例: `3: diamond_pickaxe x1, 10: stone x64`。
スロットはゲーム画面と同じです。ホットバー 1–9、メインの持ち物 10–36、その後に `offhand`、`head`、`chest`、
`legs`、`feet` です。
持ち物が空なら `持ち物は空です` と表示されます。装備だけがあるときは、その装備が表示されます。
この問い合わせはアイテムを変えません。オンラインの Bot を名前で指定すれば、runtime の持ち物のキャッシュも要求も
必要ありません。オフラインの Bot は、ワールドにいないと返します。フォームでは **インベントリ... → 持ち物を表示** が
同じコマンドを実行します。
サーバーは、通常の Xbox プレイヤーを Bot の持ち物の対象として拒否します。

`hotbar` は、画面と同じ 1–9 の番号で、選択中のスロットを表示または変更します。選択は通常の Bedrock の装備変更と
して送られ、持ち物の更新は引き続き BDS から届きます。Endbot が 2 つ目の持ち物を別に持つことはありません。
BDS は、拾ったアイテムによる持ち物の変化を、拾った本人にすべて送るわけではありません。そこで Endbot プラグインは、
BDS の実際の持ち物 36 スロットとオフハンド、防具を、設定した間隔 (既定は 4 サーバー tick) で読み、変化した
読み取り専用の観測結果を、その Bot の既存の接続で送ります。変化がなくても、定期的に補正を送ります (既定は
20 サーバー tick)。runtime は、個数や型付きの NBT も含めて一時的なキャッシュを更新します。手に持つアイテムが
変わったら、オフハンドの変化も含めて、通常の Bedrock の装備パケットで知らせ直します。これにより、同じセッションで
拾ったアイテムを、再接続せずに `hotbar`、`drop`、手に持つアイテムを使うアクションで使えます。
通常は 4 サーバー tick 以内 (20 TPS で約 0.2 秒) です。この観測が、アイテムを追加、削除、付け替えすることは
ありません。
`drop` は、引き続き BDS が検証する通常のトランザクションを使います。返事は「完了した」ではなく「要求した」と
伝えます。BDS が拒否したときは、新しい観測結果が、先回りして予測した drop も補正します。既定の設定では、変化の
ない補正に約 1 秒かかることがあります。
標準の持ち物の更新も、定期的な観測とは別に、手に持つ装備の変化を知らせます。
不明または不正な観測結果は、まるごと無視されます。選択中のスロットが不明か空なら、引き続き
`Selected hotbar slot is empty` で失敗します。対応するプラグインがないときは、届かなかった標準の差分を取り戻す
方法は、引き続き再接続です。

`swap <a> <b>` は、2 つのスタック全体の交換を要求します。ラベルは `inventory` と同じで、ホットバー 1-9、
メイン 10-36 です。片方が空なら移動になります。同じスロットどうしと、両方とも空のスロットはエラーです。
オフハンドと防具は対象外で、装備 (equip) は後回しです。例: `/bot Alice swap 10 2` はメインとホットバーの交換を
要求し、`/bot Alice swap 1 36` はホットバーのスタックを空のメインスロットに移せます。

`hold <item>` は、ID の完全一致で探します (`diamond_pickaxe` または `minecraft:diamond_pickaxe`)。ホットバーに
一致があればそれを優先し、`hotbar <n>` と同じように、一致する最小番号のホットバースロットを選びます。なければ、
一致する最小番号のメインスロットを、今選んでいるホットバースロットと交換し、そのスロットにあったスタックは
メインスロットに移ります。アイテムがないときは、指定した ID を示します。返事は要求を伝えるもので、たとえば
`hold diamond_pickaxe: ホットバー 3 の選択を要求しました` や
`hold diamond_pickaxe: スロット 14 からホットバー 1 への移動を要求しました` です。BDS で完了したことを示すもの
ではありません。

どちらの変更も、window 0 のコンテナ操作 2 つからなる従来の通常トランザクションを使い、スタック ID なしで正確な
アイテムデータを送ります。runtime は、次の確定した観測結果で補正されるまで両方のスロットを予測し、選択や手に持つ
スタックが変わった後に、選択中の装備を知らせます。**インベントリ... / アイテムを手に持つ (hold)...** はアイテム ID を
受け付け、**スロットを交換する (swap)...** には 1-36 のドロップダウンが 2 つあります。これらのフォームは、
アイテムの接頭辞も含めて、同じ意味のコマンドを表示します。
グループでの swap と hold は、既存の UUID で固定した一括入力の仕組みを使います。要求への返事は上限のある長さで、
監査と保存される履歴も付きます。
以前の組み合わせ (Windows RakNet) で、BDS は swap と hold を実際に受け付けました。人間のクライアントでのフォーム、
標準のヒント、ほかのクライアントでの装備の表示は、まだ手動の確認が残っています
([#275](https://github.com/amatouhake/endbot/issues/275))。
標準の `EndbotSwap`/`EndbotHold` の型付きオーバーロードがヒントを出します。固定している BDS の宣言ルールのもとでは、
列挙のない必須の message の末尾が、引き続き実行を担います。標準のクライアントのヒントとフォームの表示は、まだ
実機での確認が必要です。

`drop` は選択中のアイテム 1 個を、`drop stack` は選択中のスタックを要求します。`drop <slot>` は、そのスロットの
スタック全体を要求します。ラベルは `inventory` と同じで、ホットバー 1-9、メイン 10-36、その後に
offhand/head/chest/legs/feet です。
`drop <item> [count]` はアイテム ID の完全一致で探し、`stone` と `minecraft:stone` のどちらも受け付けます。個数が
なければ、一致するスタックをすべて要求します。個数 (1-10455 の整数) があれば、スロット番号の小さい順、その後に
offhand/head/chest/legs/feet の順で、その数まで取ります。足りないときは、要求した数と指定した数を示します。
1-36 の数字と装備の名前はスロットを選び、`all` と `stack` はキーワードです。それ以外の語はアイテム ID です。
キーワードやスロット名と同じ ID を区別するには、`minecraft:` を付けてください。個数はアイテムにだけ使えます。

`drop all` は、空でないスロットごとに 1 つずつ、すぐにトランザクションを要求します。オフハンドとすべての防具
スロット (ヘルメットも) も含みます。返事は要求を伝えます。例: `スロット 12 の stone x5 を落とすよう要求しました`、
`41 スロットの drop all を要求しました`。各トランザクションは BDS が検証します。
**インベントリ... / アイテムを捨てる (drop)...** には、選択中の 1 個かスタック、スロット、アイテムと任意の個数、
すべて落とすがあります。フォームは drop all の前に確認を求め、送信するコマンドを表示します。入力したコマンドは
すぐに実行されます。グループの指定も同じ書き方を使います。drop は変更を伴う操作のままで、上限のある要約、監査、
履歴が付きます。

バージョン付きの `endbot:inventory-v2` の観測結果は、正確な型付きのアイテムと NBT のデータを、上限のある断片に
分けて運びます。適用するのは、完全で正しいスナップショットがそろってからだけです。既存の
`hotbar-sync-interval-ticks` と `hotbar-sync-resend-ticks` の設定が、持ち物全体に適用されるようになりました。
サイズの上限と、残っている実機での確認は、検証の記録にあります。

`use continuous` は右クリックを押し続けます。最初の入力 tick で空中への使用の操作を送り、その後の tick では、同じ
確定した入力の流れの中でシミュレーション tick の操作を送ります。`use stop` か全体の `stop` で離します。たとえば、
ためたトライデントを投げたり、弓を撃ったりするときです。食べ物を使うには、バニラの食べる条件が必要です。
`use once` と `use interval` は短く押して離すアクションのままで、食べたり、アイテムを最大までためたりするほど
長くは押しません。ホットバーのスロットを切り替えても、前のアイテムを離します。トライデント、弓、金のリンゴは BDS で
確かめました。ほかのアイテムと、ディメンションの移動後の使用は確かめていません
([#275](https://github.com/amatouhake/endbot/issues/275)、[#274](https://github.com/amatouhake/endbot/issues/274))。

`use for <ticks>` は、1–72000 の runtime 入力 tick の間 use を押し続け、自動で離します。たとえば
`/bot Alice use for 40` は、2 秒押して離す動作を 1 回要求します。弓やトライデントをためるのに向いています。
これは runtime の 20 Hz の入力 tick です。サーバーの遅れやバニラのアイテムの条件は、引き続き結果に影響します。
押す時間は、最初の空中への使用のトランザクションから数え始めます。保留中のブロック操作がその入力 tick を使って
いるときは、use は押す時間を消費せずに待ちます。最初の使用の前に止めると、離す操作を送らずに取り消されます。
最初に手が空なら何も起きず、後で拾うアイテムを待って使うことはしません。
返事は要求を確認するもので、撃てたことや食べたことを示すものではありません。これは時間の指定で、アイテムの個数や
完了の条件ではありません。食べ物は、早く食べ終わることも、長く押すと繰り返すことも、バニラの前提条件を満たさずに
失敗することもあります。
`use stop` と全体の `stop` は早めに離すので、ためたアイテムが発射されることがあります。ホットバーを明示的に選んでも、
時間指定の use は離されて取り消されます。死亡、ディメンションの移動、切断では破棄されます。新しい時間指定の use の
コマンドは前のものを置き換え、押す時間と期限を新しくします。時間が終わっても、移動やほかの入力は続きます。
再接続の後に再開するものはありません。既存の `use`/`once`、`continuous`、`interval` の動作も、引き続き使えます。

<a id="durations-for-and-charged-presses-hold"></a>
### 時間の指定 (`for`) とためる押し方 (`hold`)

`for <ticks>` は、入力をどれだけ続けるかを指定します。すべてのアクション、移動、連続採掘で使えます:

```text
/bot Alice move forward for 40                 2 秒間前に歩いて止まる
/bot Alice jump for 100                        100 tick の間、毎 tick ジャンプ (jump continuous for 100 と同じ)
/bot Alice attack interval 20 for 200          200 tick の間、20 tick ごとに攻撃
/bot Alice use for 40                          40 tick use を押し続けて離す (従来どおり)
/bot Alice use hold 30                         30 tick ためて、1 回離す
/bot Alice use hold 30 for 200                 30 tick ためて離す動作を、200 tick の間続けて繰り返す
/bot Alice use hold 30 interval 40 for 200     200 tick の間、40 tick ごとに 30 tick のためを始める
/bot Alice destroy for 200                     200 tick の間、連続採掘
/bot Alice destroy count 64                    64 ブロック壊すまで連続採掘
```

モードがなければアクションは `once` で、`for` があれば `continuous` です。`once ... for` と `stop ... for` は
拒否されます。1 回押すだけのものに長さはないからです。`interval`、`hold`、`for` の句はどの順で書いてもよく、
それぞれ 1 回までです。`interval` は `once`/`continuous` の代わりになります。値はすべて 1–72000 の runtime 入力
tick (1 秒に 20) です。

`for` はコマンドから (次の入力 tick から) 数えるので、入力はちょうどその tick 数だけ続きます。例外は 1 つだけで、
既存の単純な `use for <ticks>` / `use continuous for <ticks>` です。これは今までどおり最初の空中への使用から数える
ので、遅れた押下がためる時間を食うことはありません (上を参照)。時間が終わると、その入力だけが止まります。移動、
ほかのアクション、スプリント / スニーク、採掘は続きます。同じ入力への新しいコマンドは期限を置き換え、`for` のない
コマンドは期限を外します。全体の `stop`、`<input> stop`、死亡、切断で早めに終わります。`status` は、自分で終わる
入力を残りの tick 数とともに表示します。例: `時間指定: move forward 残り 30 tick, use interval 40 hold 30`。

`interval` のアクションは繰り返すコマンドなので、最初に使ったアイテムより長く続きます。スタックを使い切ったり
(ポーションを飲んだ)、手が空になったりしても、終わるのは進行中の押下だけです。次の発動では、そのとき手に持って
いるものを使います。手が空のときの発動は何も送らず、次の間隔を待ち続けます。`once`、`continuous`、単純な
`use for` は今までどおり、アイテムを使い切ったり、ホットバーのスロットが変わったりすると、自分で取り消されます。

`count <blocks>` は、`for` に対応する destroy だけの完了条件です。その数のブロックがなくなったら連続採掘を止めます
(1–72000)。ブロックの間の待ち時間は数に入りません。`for ... count ...` は、どちらの順でも先に来たほうで終わります。
ほかの入力でのアイテム個数の条件は実装していません。

`hold <ticks>` (use だけ) は、1 回押すたびにその数の use トランザクションの間押し続けてから離します。`use for` と
同じ押して離す動作なので、弓やトライデントを繰り返し撃てます。`for` もモードもない `hold` は、1 回だけためます。
`hold ... for` (または `continuous hold`) は、離した tick の直後に次のためを始めます。`hold ... interval <ticks>` は、
interval の tick ごとにためを始めます。離す操作がそれぞれ自分の tick を持てるように、interval は hold より長くする
必要があります。ためている途中で `for` の期限が来ると、すぐに離すので、ため切っていないアイテムが発射されることが
あります。避けるには、押す周期の倍数を選んでください。時間指定の use と同じく、hold はホットバーの選択、手に持つ
アイテムの変化や空になること、ディメンションの移動、死亡、切断で取り消され、再接続の後に再開することはありません。
離すたびに確認されるのは入力だけで、撃てたことではありません。

ジャンプ (jump)、攻撃 (attack)、アイテムを使う (use)、歩く (move)、ブロックを壊す (destroy) のフォームでも、同じ
`interval`、`hold`、`for` の句を使えます (ブロックを壊す (destroy) のフォームでは、continuous モードに `count` が
加わります) ([操作フォーム](#control-forms)を参照)。

`use` は、食べ物、弓、トライデントのように、選択中のアイテムを空中で使ったり押し続けたりすることです。`interact` は、
指定したブロックの面への通常の右クリックです。protocol-2193 の押下、サーバー側で判定するアイテム操作の tick、
離す操作の流れを送ります。届く距離、可否、当たり判定、設置、持ち物の減少は BDS が決めます。そのため、選択中の
アイテムが置けるものなら、プラグインがワールドを編集しなくても、サバイバルでブロックを置けます。`drop` は選択中の
アイテムを 1 個落とし、`drop stack` は選択中のスタックを、通常の持ち物のトランザクションで要求します。より広い
指定も、観測した正確なアイテムデータで、同じ従来のコンテナからワールドへの経路を使います (上の持ち物と drop の
書き方を参照)。

<a id="areas-within-and-except"></a>
### 範囲: `within` と `except`

1 つの範囲の値で、操作が選べるブロックを絞り込みます。`within <area>` は範囲の中のブロックだけを残し、
`except <area>` は範囲の中のブロックを外します。どちらも同じ形を受け付け、値の数で形が決まります:

| 範囲 | 形 | 例 |
| --- | --- | --- |
| `<x> <y> <z>` | 1 ブロック | `except ~ ~-1 ~` (Bot の足元のブロック) |
| `<x1> <y1> <z1> <x2> <y2> <z2>` | 直方体。`/fill` と同じく両方の角を含む | `within ~-3 ~ ~-3 ~3 ~10 ~3` |
| `<r>` | Bot を中心とする半径 `r` の球 | `within 6` |
| `<r> of <x> <y> <z>` | ある地点を中心とする半径 `r` の球 | `within 4 of 10 70 -3` |

ほかの個数は書き方の誤りです。今後の形は、先頭に形の単語を付けます (`within cylinder ...`)。意味はどこでも
同じです:

- 範囲は候補を絞るだけです。届く距離や視線を広げることはありません。`destroy` と `interact` は 6 ブロックの
  届く距離と視線のままで、`blocks` が Bot から 16 ブロックより先を見ることはありません。
- `~` (と `<r>` の中心) は、コマンドを受け付けた時点の Bot を基準に決まります。そのため、連続採掘は Bot が動いても
  同じ範囲を使います。
- `within` は最大で半径 16 の球 (17157 ブロック) までです。それより大きい直方体は拒否されます。`except` には
  上限がありません。
- 範囲がなければ、各操作は既定の動きのままです。`blocks` は Bot から半径 8 の球を探し、入力した `destroy` と
  `interact` は届くものすべてから選び、視線での連続採掘は照準の先にあるものを掘ります。
- Bot の足場は特別扱いしません。守るには `except ~ ~-1 ~` を明示します。
- チャットでは、`within` と `except` はほかの句と同じくそれぞれ 1 回までで、操作の後ならどこにでも書けます。Luau の
  スクリプトでは、`area:minus()` で複数の除外をつなげられます ([スクリプトでの範囲](../SCRIPTING.md#areas)を参照)。

範囲は、`blocks <type>`、`destroy <block type>`、`destroy continuous` (`for`/`count` による場合も)、
`interact <block type>` に使えます。連続採掘は、対象を選び直すたびに範囲を当てはめます。照準が範囲の外にある
視線での連続採掘は、何も見えていないときと同じように待ちます。座標、照準の 1 ブロック、`@` のエンティティには
範囲を付けられません。`blocks ... radius` と `blocks ... at` は廃止され、`within <r>` と
`within <r> of <x> <y> <z>` に変わりました。古い書き方は、新しい書き方を示すメッセージで失敗します。
`/bot help area` で、ゲーム内に表を表示できます。

<a id="targets-crosshair-coordinates-block-types-and--entities"></a>
### 対象: 照準、座標、ブロックの種類、`@` のエンティティ

左クリックと右クリックの動詞は別々のままですが (`attack`/`destroy`、`use`/`interact`)、対象は共通の書き方を
使います (2026-10-24 に決定):

| 形 | 対象 | 例 |
| --- | --- | --- |
| なし | Bot が見ているもの | `interact`、`destroy`、`attack` |
| `<x> <y> <z> [face]` | そのブロック。`~` は Bot からの相対。面がなければ Bot に向いた面 | `interact ~~-1~`、`destroy 1 64 2 up` |
| `<block type>` | Bot が 6 ブロック以内で届く、その種類のいちばん近いブロック | `interact chest`、`destroy oak_log` |
| `@<type\|id\|nearest>` | 一致するプレイヤー以外のいちばん近いエンティティ (`interact` は 6 ブロック以内、`attack` は 4.5 以内) | `interact @cow`、`attack @zombie`、`interact @9` |

`@` はバニラのエンティティセレクターの記号にならったもので、`entity @cow` や id (`interact @9`) も含め、すべての
エンティティで必要です。一覧では id をこの形で表示し (`cow @9 (3.4m)`)、スクリプトのデータでは `selector` として
運びます。

対象は繰り返しと組み合わせられます。`attack @zombie continuous|interval <ticks>|for <ticks>` は、発動のたびに
いちばん近い一致に狙いを付け直し、届く範囲にいなければ何もしません。照準の先に切り替えることはないので、そこに
いるプレイヤーを叩くことはありません。`interact @cow count 5` (または `interval`/`for`) は、このジョブでまだ
クリックしていない一致するエンティティが届く範囲にいればそれを、いなければいちばん前にクリックしたものを右クリック
します。そのため、群れに 1 頭ずつえさをやれます。`count` は、エンティティに送った右クリックか左クリックの回数を
数えます。結果は引き続き BDS が決めます (すでに繁殖モードの牛は何も食べません)。クリックのたびに、次のクリックは、
BDS がそのクリックで変わった手持ちのアイテム (食べた小麦、すり減った剣) を報告するまで、最大 10 tick 待ちます。
古い手持ちのアイテムのままのクリックは拒否されるからです。`once` は 1 回のクリックで、`attack @cow stop`、
`interact stop`、`stop` で終わります。`status` は、実行中の対象と残りのクリック数を表示します。例:
`interact @cow continuous 残り 2 回`。`destroy oak_log count 10` (または `continuous`/`for`) は連続採掘で、
1 ブロックごとに、見えているその種類のいちばん近いブロックのほうを向き、届く範囲になければ待ちます。歩くことは
ありません。不明なブロックの種類はそのように報告され、`destroy @…` は `attack` を案内します。Luau では
`bot:interact("@cow")`、`bot:interact("chest")`、`bot:destroy("oak_log")`、`bot:attack("@zombie")` です。
実機での確認 (2026-10-24、Windows RakNet、コンソール): `interact @cow` で牛にえさをやり、照準での `interact` が
牛に届き、`attack @cow` でダメージを与え、`destroy dirt` でいちばん近い土ブロックを壊しました。修正後の実機での
確認 (2026-10-24): `interact @cow count 3` で別々の牛 3 頭にえさ (小麦 3 個) をやり、`destroy oak_log count 5` で
原木 5 個の幹を壊しました。手持ちのアイテムを待つ処理を入れる前は、最初より後の素早いクリックが BDS に拒否されて
いました。

<a id="looking-around"></a>
### 周囲の確認

`/bot` のどこでも、座標はバニラの詰めた相対の書き方を受け付けます。`~~-1~` は `~ ~-1 ~` です。`inventory` と
`hotbar` は、道具と防具について、残りと最大の耐久値を表示します。例: `iron_pickaxe x1 (210/250)`。`hotbar` は、
選択中のスロットだけでなく、ホットバーのアイテムも一覧にします。`entity [@<type|id|nearest>]` は、16 ブロック
以内のエンティティ 1 体を詳しく表示します (id、距離、位置、体力、名札)。引数がなければ、いちばん近いものです。

`target` は、Bot の照準が 6 ブロック以内で当たるものを表示します。ブロック (位置、面、種類) とプレイヤー以外の
エンティティのうち、近いほうです。`block <x> <y> <z>` は、1 つのブロックの種類と状態、そして Bot が今それを狙えるか
(届く、届かない、または何がさえぎっているか) を表示します。`~` は Bot からの相対で、30000000 を超える座標は
拒否されます。`blocks <type>` は、その種類のいちばん近いブロックを `x y z (distance)` の形で、Bot に近い順に表示
します (`limit` 件の一致が確定したら、読むのをやめます)。探すのは Bot から半径 8 の球か、指定した
[範囲](#areas-within-and-except)の中で (Bot から 16 ブロックより先は探しません)、最大 `limit` 件 (既定は 10、
最大 64) です。数えるのはプレイヤーに見えるブロック (空気、液体、植物、葉、ガラス、氷、またはハーフブロックや
フェンスのような部分的な形に面が接しているもの) だけなので、埋まっている鉱石はわかりません。Bot が今狙えるものには
`届く` の印が付きます。高い構造物は、大事な高さの周りの範囲で探します。例: `blocks oak_log within 5 of ~ ~8 ~`。
`~` は Bot からの相対です。この 3 つはどれも Endstone SDK を通して BDS を読み、何も変えず、スクリプトにはデータを
返します。グループを対象にすると、`status` と同じく各メンバーの結果を表示します。ゲームプレイのフォームの
**周囲を確認...** で、近くのエンティティの一覧と一緒に使えます。

<a id="entities-and-vehicles"></a>
### エンティティと乗り物

`entities` は、Bot から 16 ブロック以内のプレイヤー以外のエンティティを、近い順に最大 10 件、
`<type> @<id> (<distance>m)` の形で表示します。グループを対象にすると `status` と同じ問い合わせになり、各メンバーの
一覧が表示されます。履歴や監査の記録は残りません。`interact @<type|nearest|id>` は、6 ブロック以内で一致する
いちばん近いプレイヤー以外のエンティティを選びます (`cow` と `minecraft:cow` は同じです。`nearest` は、落ちている
アイテム、経験値オーブ、飛び道具、エフェクト以外のどの種類でも選びます。id は `entities` で調べます)。そして Bot を
そのほうへ向け、次の入力 tick で、手に持ったアイテムで右クリックします。これはバニラのクライアントと同じ経路
(action が `interact` の `item_use_on_entity`) です。えさやりと繁殖では手に持ったアイテムを消費し、ハサミは毛を
刈り、名札は名前を付けます。空の手でトロッコ、ボート、乗れる動物をクリックすると乗ります。結果はすべて BDS が
決めます。返事は要求を確認するだけです。

乗っている間、Bot は BDS が送る乗り物の位置に従い、自分の移動の予測は使いません。`status` と Bot の画面には
`<type> に乗車中` と表示されます。乗っている Bot は、プレイヤーと同じように、別の乗り物を `interact` して乗り換え
られます。`nearest` は、乗っている乗り物を飛ばします。`dismount` は、バニラの乗り物から降りる操作を送ります。
バニラのクライアントと同じく、降りる場所は乗っている側が選びます。プラグインは隣のブロックを調べ、固い床と、その
上に通れるブロックが 2 つある場所を、乗り物と同じ高さ、1 つ上、1 つ下の順に探します。トロッコでは、進行方向に
対して [Minecraft Wiki](https://minecraft.wiki/w/Minecart#Dismounting) の順 (右、左、右後ろ、左後ろ、右前、左前、
後ろ、前) を使います。ボートでは、Bot の向いている方向を優先します
([Boat#Exiting](https://minecraft.wiki/w/Boat#Exiting))。ほかの乗れるものも同じ輪を使い、Bedrock の既定の
「エンティティの周りの有効な地面の位置」に合わせています。ブロックが通れるかどうかは、安全側に倒した名前の一覧で
判定します (不明なブロックは固いものとします)。
空いている場所がなければ、Bot は乗り物があった場所にとどまります。降りる地点はそのブロックの中に収まり、乗り物の
当たり判定とブロックの端から 0.05 離れます。そのため、Bot がボートの縁や隣のブロックの上に乗ることはありません。

runtime にはワールドの当たり判定がありません。BDS が位置を補正したときに落下を始めます。BDS は、ボート (または
ほかの上に立てるエンティティ) が近くにあるとその補正を省くので、ボートの隣で床を取り除かれた Bot が空中に立って
いました。現在は、プラグインが hotbar の同期間隔ごとに、ブロックの上面に立っている Bot の足の当たり判定の下に固い
ブロックがあるかを調べ、なければ runtime に落下を始めるよう伝えます。着地は BDS が補正します。半端な高さ
(ハーフブロック、カーペット)、水、飛行、ボートやシュルカーの上に立っている場合は、報告しません。BDS は、乗っている
者が報告する位置は無視しますが、つながりが切れた直後の横向きのジャンプは補正します。そのため Bot は、乗ったまま
2 tick の間、降りる地点を報告してから、降りる操作を送ります。こうすると、降りた後の最初の入力で位置がずれません。
保留中の `dismount` があるときの 2 回目の `dismount` は拒否されます。BDS が 40 tick 以内に降りたことを確認しなければ、
Bot は乗っている扱いをやめます。実機での確認 (2026-10-24): 降りずにトロッコからボートへの乗り換え、向いている
方向へのボートからの降車、動いているトロッコからの横への降車を確かめ、どれも補正はありませんでした。馬やボートの
操縦は実装していません。実機での確認 (2026-10-24、Windows RakNet、固定した組み合わせ): 牛にえさをやると小麦が減り、
Bot は id でトロッコに乗り、動力付きのトロッコで約 12 ブロック移動する間 BDS がトロッコの上の位置を保ち、乗って
いる間の操作を拒否し (乗り換えの実装より前)、止まっているトロッコと動いているトロッコのどちらから降りた後も普通に
歩けました (`scripts/raknet_spike.py --entity`)。

コマンドの宣言では、解析できることと入力補完を分けています。実際の BDS のオーバーロードの照合で、次の 3 つの
ルールが判明したためです (文書にある 42 の書き方を本物の `compileCommand` の経路で実行する試験用プラグインで
確かめました)。末尾の省略可能なパラメーターは入力を受け取らない。`string` は数値の語を拒否する。列挙の後ろに置いた
パラメーターは一致しない。そのため、末尾を受け取るものは、前に列挙のない必須の `message` でなければなりません。
一方、候補の表示には、別々のオーバーロードの同じ位置に列挙が必要です:

```text
/bot [command: string] [topic: string]
/bot (ping|list|help)<command: EndbotRoot>
/bot <command: string> <page: int>
/bot <name: string> <operation: string>
/bot <name: string> <operation: string> <arguments: message>
```

`<name>` の文字列のオーバーロードが、解析できるようにするための層です。2 語の書き方と、それより長い名前付きの
書き方をすべて受け付けます (数字のヘルプページは、文字列が数値を拒否するので、代わりに必須の int のオーバーロードを
使います)。その下の型付きの列挙のオーバーロード (操作、移動の方向、アクションのモード、on/off、ディメンションの
別名、ブロックの面、`stack`) は、入力補完に候補を出すためにあります。しかし実際の Minecraft クライアントでの確認では、
互換性のある汎用の文字列の分岐が残っている限り、UI をきれいに絞り込めませんでした。汎用のオーバーロードが表示された
ままになり、絞り込みを支配します。名前が先に来る `/bot` でも、選択モデルの `/botprobe` (コマンドパーサーの調査で
使った一時的な診断用の試験コマンドで、Endbot に含まれるコマンドではありません) でも同じでした。数値の語のほうが
よく絞り込めるのは、汎用の `string` の分岐を除外するからにすぎません。広い `<operation: message>` の予備の分岐は、
名前付きの操作の候補をすべて吸い込んでしまうので、すでに不採用になっています。この固定している Endstone 0.11 の
基準では、そのため入力補完より実行を優先しています。文書にある書き方はすべて解析できますが、入力補完は不完全な
ままです。コマンドの宣言のより深い作り直しは、上流の Endstone のコマンド API の作業 (Brigadier 風の型付きコマンド
ツリー、上流の PR #509) が成熟するまで先送りします。この構成は意図した互換性のための暫定策で、最終的なコマンド API
ではありません。固定している Endstone の公開 API は、Bot のプロファイル名の動的な補完をサポートされた形で提供して
いないので、名前は文字列のままです。名前を調べるには `/bot list` を使ってください。Endbot は、非公開のレジストリや
生の soft enum のフックは使いません。

<a id="shared-group-menus-and-results"></a>
## グループの共通メニューと結果

グループ機能は、`/bot menu` にグループの操作対象を直接加えます。`/botgroup` だけ、または `/botgroup menu` は、
グループの閲覧と作成を開きます。`/botgroup menu #miners` は、メンバーの閲覧とメンバーの管理を開き、その中に
**グループを一括操作...** の項目があります。`/bot #miners menu` は、テレポート、接続の管理、チャンク半径も含めて、
共通の Bot の操作画面を直接開きます。中から開いた操作画面から戻ると、管理から入ったときは管理に、直接入ったときは
Bot と対象の一覧に戻ります。**グループ管理...** は、選んだグループの管理画面へ戻るリンクです。管理から入ったときは、
代わりに既存の **グループの管理へ戻る** ボタンを使います。
各メンバーは、通常の Bot の画面を開きます。グループの削除には確認があり、Bot は残ります。フォームは同じ `/bot` や
`/botgroup` のコマンドと権限チェックを表示して送信し、UUID とメンバーの確認で古いフォームを拒否します。

グループの持ち主は `/botgroup` で扱います:

```text
/botgroup visibility #group shared|private
/botgroup owner #group <GamerTag>
```

持ち主かコンソールは、グループの公開範囲を `shared` か `private` にできます。持ち主のいないグループは共有のままで、
拒否されたときは `owner` が案内されます。グループの持ち主を変えられるのはコンソールだけで、GamerTag はオンラインの
プレイヤーかコントローラーでなければなりません。非公開のグループは、ほかのプレイヤーの一覧に表示されず、その
プレイヤーからは見つからない扱いになります (S4)。

グループ全体への変更を伴うコマンドの受付の返事と、その通常の監査の記録は、2 行までに収めます。内容は数と、まとめた
失敗の分類で、グループや失敗の数によらず 2 行です。これは受け付けたことの確認で、ワールドでの動作が完了したこと
ではありません。詳細は、メニューを使わずに `/botgroup result #miners [history]` で見られます。これは 1 つの操作に
ついて、各メンバーの結果を表示します。番号を省くか `1` で最新、`2` で 1 つ前の操作、のように指定します。メニューは
同じ保存済みの結果を `/botgroup menu #miners result [history]` で読み、新旧を切り替えるボタンがあります。保持するのは
実行者とグループごとに最大 20 操作、全体で 128 操作までで、古いものから消します。結果は実行者とグループごとの非公開で、
メモリにだけあり、再起動で消えます。入力を送った後に応答が得られなかったときは、受付不明として報告します。全体の
動作と残っている確認は、[グループの範囲、根拠、クライアントでの確認](../GROUPS.md)を見てください。

問い合わせはデータを直接返します。`/bot #miners status`、`/bot #miners inventory`、`/bot #miners hotbar`、
`/bot #miners radius` は、各メンバーの問い合わせの結果を、`#group[index]` と Bot の名前を付けて表示します。失敗は
そのメンバーの結果の行に入り、残りのメンバーも引き続き問い合わせます。番号付きの問い合わせも同じです。問い合わせは
監査の記録を作らず、`result` の履歴も変えません。そのため、操作の後に状態を確かめても、その操作が最新の操作結果の
ままです。`hotbar <slot>` と `radius <value|default>` は変更を伴う操作のままで、上限のある要約と保存される履歴が
付きます。

<a id="scripts-and-triggers"></a>
## スクリプトとトリガー

スクリプトは、オペレーターが有効にしたサーバーで使えます ([準備](../SCRIPTING_SETUP.md))。まず
[チュートリアル](../SCRIPTING_TUTORIAL.md)から始めてください。[SCRIPTING.md](../SCRIPTING.md) がリファレンスです。
実行には始めた人の権限が使われ、操作のたびに確かめ直します。実行はログアウトしても続き、止めるか権限が取り消される
まで続きます。

```text
/botscript list
/botscript show <name> [page]
/botscript run <name> [positional arguments...]
/botscript runs
/botscript stop <run-id|name>
/botscript delete <name>
/botscript help
/botscript menu
/botscript trigger add <script> <kind> [field=value ...] [name=<name>] [visibility=shared|private] [-- <arg> ...]
/botscript trigger list
/botscript trigger show <name>
/botscript trigger enable <name>
/botscript trigger disable <name>
/botscript trigger remove <name>
/botscript trigger set <name> <policy>=<value> ...
/botscript trigger visibility <name> shared|private
```

スクリプトが有効なら、`/bot menu` に **スクリプト...** (**+ ここに新しい Bot** の後) が加わります。共有のソース、
行ごとの編集と本での編集、テンプレート、パラメーターのフォーム、各スクリプトの画面でのソースの表示、コントローラー
ごとの停止、確認つきの削除があります。入力の `save` ではソースを書けません。順番どおりの実行の引数は、スクリプトの
宣言の順に並べ、その後に `name=value` を書きます。座標は引用符で囲みます。例:
`/botscript run row #miners "~ ~ ~" 2`。実行は再起動の後に再開しません。スクリプトを無効にしても、ソースは残ります。

**トリガー** は、イベントの種類とフィルタをスクリプトに結びつけ、そのイベントが起きるたびにスクリプトを始めます。
スクリプトは `param.event("event")` を宣言します。`trigger add` と `trigger enable` は、スクリプトの宣言と
パラメーターを承認します。そのため、トリガーを有効にできるのは、そのスクリプトを実行できる人だけです。`area=` は、
`within` と同じ範囲の値を、引用符で囲んだ 1 つの語として受け付けます (`"100 64 200"`、`"0 64 0 3 65 3"`、
`"5 of 0 64 0"`)。`except <values>` を付けることもできます。`--` の後はスクリプトの引数です。`trigger set` は
`concurrency`、`cooldown` (tick)、`startsPerMinute`、`queue` を受け付けます。コンソールは、ほかの持ち主の
トリガーを `<owner>/<name>` (表示名か持ち主のキー) で指定します。上限:
`[limits] max-triggers-per-controller` (既定は 8、`0` でトリガーを無効にします) と `max-watched-blocks-per-controller`
(既定は 1024)。一時停止、無効化、ポリシーの既定値は、
[SCRIPTING.md](../SCRIPTING.md#triggers) を見てください。

<a id="operational-states"></a>
## 接続状態

- `connecting` (接続中): 要求したセッションが、まだ spawn していません。
- `online` (オンライン): プロトコルのセッションが動いています。
- `reconnecting` (再接続中): 明示的な再接続か、回数に上限のある自動の再試行が進んでいます。
- `offline` (オフライン): 目標の状態として、意図してオフラインにしています。
- `failed` (失敗): 再試行を使い切りました。status に最後のエラーが入ります。

Bot ごとの世代と再接続のタイマー、入力は、ほかのすべての Bot から独立しています。予期しない切断では、プロファイルの
UUID を保ち、30 秒を上限とする指数バックオフで再試行し、設定した試行回数で止めます。明示的な再接続とオンライン中の
名前の変更は、置き換える前に古い接続が閉じるのを待ちます。そのため、新しいセッションが古いセッションと競合する
ことはありません。
